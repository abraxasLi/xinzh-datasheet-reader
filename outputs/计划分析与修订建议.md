## 一、你的计划里判断对的部分

这几条不是客套，是这次实测后被证实的：

1. **只做两件事**（中文搜索定位、原文跟随式译读）。没有滑向"通用问答机器人"，产品边界清楚，验收也能量化。
2. **本地优先**：不登录、不要密钥、PDF 不出本机。这次端到端验证里，PDF 索引、搜索、翻译全部发生在 127.0.0.1，进程外没有任何请求。
3. **承认"词典 ≠ 翻译"并坚持标注边界**。这是整个计划里最重要的自我约束，也是这次能把真实模型接进来的前提。
4. **拿 RM0008 当验收样本、写验收记录**。搜索验收记录里"过宽问题只给部分命中、无证据就返回无结果"的态度是对的，比刷一个好看的数字有用。
5. **坚持先用最小可运行证明（M4 rule 9）再谈集成**。这次正是靠它一次性排掉了"模型能不能跑"这个悬了三周的不确定性。

## 二、我判断风险最大的五个地方

### 1. 整个产品押在一个没验证过的 70 MB 模型上，且没有降级路径

原计划的事实是：模型下载 403、安装会把 PyTorch/Stanza 拖进来、许可没核实、速度没测、质量没测。在此之前，所有"跟随译读"的价值都是假设。

这次实测结论（详见 `outputs/M4-离线整段翻译最小验证.md`）：

- **能跑，而且不重**：Argos `translate-en_zh` 1.9 包（70,743,021 字节）里就是 CTranslate2 的 `model.bin` + SentencePiece。**不装 PyTorch、不装 Stanza**，只用 `ctranslate2` + `sentencepiece`（约 22 MB 轮子）就能推理。冷启动 133–191 ms，单段 56–142 ms。
- **许可有据可查**：包内 README 写明 "The original OPUS model from which this packaged model is derived is licensed CC-BY 4.0"。这只能作为模型来源的证据，**不能替代对训练数据的单独核对**；界面里把原文原样展示。
- **质量是"能读"而不是"可信"**：寄存器名、地址、数值、单位基本能保住（有占位保护后更好），但会出现 `披针`（pins）、`坦佩尔事件`（Tamper event）、`备份登记器`（backup registers）这类错误，否定句和条件句的语序也常丢。**这就是 OPUS-MT 的水平**，不要再指望通过换参数解决。

→ 结论：**它是可用的底线方案，不是产品的护城河**。必须在界面上写"机器翻译，请核对原文"，并且靠"标识符占位保护 + 术语校正"兜住工程含义。

### 2. Next.js 是这个产品不合适的底座

不是"能不能用"的问题，是"为本地单机应用背了多少不必要的负担"：

- 开发/构建都要 fork 子进程并用 IPC 管道；我这台机器的沙箱直接把 `next dev` 和 `next build` 拦成了 `spawn EPERM`，只能临时放开权限才能跑。
- 交付要 `next build` + standalone + 自带 Node 运行时，再加 Python 运行时和模型，EXE 体积和启动时间都会很难看。
- 这个应用不需要 SSR、不需要 API 路由这层抽象：所有逻辑都在本机同一个进程里，PDF.js 在浏览器侧，索引和翻译在本地服务侧。

→ 我这次保留了原型（因为 PDF 阅读器、搜索结果面板是可复用资产，重写不划算），但**建议在 M6 之前把外壳换成 Electron 或 WebView2 + 一个几百行的本地 HTTP 服务**。真要留 Next，就只接受 `standalone` 输出，并先量体积。

### 3. "段落级翻译"忽略了数据手册的主体是表格

这是我认为最值得改的产品判断。RM0008 里初学者卡住的地方，绝大多数不是整段英文散文，而是：

- 位域表：`Bits 26:24 SWJ_CFG[2:0]`、`rw`、`0: No effect 1: Reset` 这种行列结构；
- 电气特性表、引脚定义表、地址映射表。

段落悬停只能覆盖寄存器说明里那一两句解释，**表格里的内容仍然是英文**。而表格恰恰是"结构化"的——位名、位宽、读写属性、每种取值的含义，都可以在不用模型的情况下生成可靠中文（术语库 + 模板 + 表格结构），比散文机翻可信得多。

→ 下一阶段我认为**优先级最高**的是"表格即译文"：把 PDF 里的位域表还原成行列（本来坐标就有），渲染成中文表头 + 中文取值说明，并保留位名/地址/复位值原文。这比继续调段落译文对初学者的收益大一个量级。

### 4. 中文搜索的架构是"手写意图正则 + 词典"，验收集恰好是它擅长的那 20 条

`retrieval.ts` 里 16 条 `inferRegisterIntent` 正则，等于把验收用例的答案写进了代码。20 条能过，换一本手册、换一个外设就塌。

→ 建议改成三层：

1. **文档内实体索引**（真正的护城河）：从文字层抽寄存器名、位域名、`Address offset`、`Reset value`、`rw` 属性、章节标题、表标题，建成带坐标的实体表；
2. **双语术语扩展**（中文 → 英文候选），词典只负责"翻译问题"，不负责"猜答案"；
3. **可解释打分**：命中实体定义 ≫ 正文提及；候选列表带"为什么是它"的证据。

意图正则退回成兜底。这样换手册时，退化是"候选变多"，而不是"直接搜不到"。

### 5. 把 EXE 放到最后（M6）风险太大

模型运行时（Python + CTranslate2）直接决定打包方式、体积、启动时间。越晚定，返工越贵。

→ 现在就该拍板二选一：

- **A. 随包 Python**：约 +45 MB（嵌入式 Python + 两个轮子），CTranslate2 速度快，改动最小；
- **B. 全 Node 推理**：换 ONNX Runtime + 量化模型（约 119 MB），去掉 Python，但 CPU 生成速度大概率比 CTranslate2 慢。

我倾向 A（先能用），把 B 当体积优化项。无论选哪个，都应该在 M5 阶段就把"EXE 里怎么启动翻译服务"跑通一次，而不是等界面全做完。

## 三、我这一版实际做了什么（和你原计划的差异）

保留：PDF.js 阅读器、页码/缩放/目录、搜索结果面板、悬停延迟、固定段落、原文/译文/对照切换、中文搜索的术语映射。

替换或新增：

| 项 | 原状 | 现在 |
| --- | --- | --- |
| 段译引擎 | 词典规则（假装翻译） | Argos 1.9 + CTranslate2 精简运行时，本机 127.0.0.1 服务，常驻内存 |
| 模型管理 | 无 | 安装/状态/移除/许可展示，安装只需选本地 `.argosmodel` 文件，0.7 秒解包校验 |
| 标识符保护 | 无 | 寄存器名/位名/`0x` 地址/数值+单位→`[[Zn]]` 占位，译后还原（实测 `14 MHz`、`1.5 us`、`VDD`、`VBAT` 均保住） |
| 输出术语校正 | 无 | 小表兜底（如"披针→引脚"），并明确标注是机器翻译 |
| PDF 渲染 | 缺 PDF.js viewer 样式，文字层没有绝对定位 | 引入 `pdf_viewer.css`，页面/文字层/高亮按坐标对齐 |
| 验收 | 只有搜索 20 条 | 新增 M4 最小证明、端到端接口验收、浏览器截图验收（含窄屏） |

一个重要的工程细节：**CTranslate2 / SentencePiece 的 C++ 实现用 `std::ifstream` 打开模型文件，在 Windows 上无法处理非 ASCII 绝对路径**（本项目目录名是中文）。解决办法是先 `chdir` 到模型父目录、再用相对路径传进去。换机器或改目录名时，这个坑会回来。

## 四、按 ROI 排序的下一步建议

1. **位域表格翻译**（结构化，不依赖段落机翻）：解析 `Bits x:y NAME[..]:` 行 + `0/1` 取值说明，生成中文表格视图。
2. **实体索引重构**：寄存器/位域/偏移/复位值/章节标题入索引，搜索从"猜意图"变成"查实体"。
3. **译文质量闭环**：20 段人工评分表（术语、否定、条件、数值、单位五列），沉淀失败模式，再决定换不换模型。
4. **EXE 先跑通一次**：Electron/WebView2 + 内置 Python 运行时，量体积和冷启动，再回来优化。
5. **阅读体验**：连续滚动、当前段与译文联动、键盘流（↑↓ 跳段、Tab 逐段）。

## 六、明确没有做到的事

- EXE 没有生成，也没有在无 Node 的环境里验收。
- 表格翻译、连续滚动、跨手册泛化都没有做。
- 翻译质量只做了 3 段最小证明和若干样例，**没有做 20 段人工评分**，不能声称"质量合格"。
- 模型许可只核到包内 README（OPUS 原始模型 CC-BY 4.0），**训练数据与再分发条款未核**。
- 搜索仍是原来的正则/词典架构，没有按建议重构。
